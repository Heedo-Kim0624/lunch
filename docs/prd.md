# PRD — Lunch Machine MVP

## Problem

점심 메뉴를 고르는 데 매일 작은 결정 피로가 발생한다. 기존 랜덤 뽑기는 빠르지만 사용자의 취향과 최근 식사 흐름을 배우지 못한다.

## Product Promise

사용자는 레버 한 번으로 지금 먹기 좋은 음식 하나를 받는다. 서비스는 수락과 재추천 행동을 기록해 다음 선택을 조금 더 개인화한다.

## Primary User

- 로그인 없이 빠르게 시작하거나, 계정으로 여러 세션의 취향 기록을 이어가고 싶은 사용자
- 한국 외식 메뉴를 중심으로 빠르게 한 가지 결론을 원하는 사용자

## MVP User Flow

1. 사용자는 필요하면 기계 상단 라벨을 눌러 온도·종류·나라·맵기를 복수 선택한다.
2. 사용자가 접근 가능한 실제 버튼 형태의 레버를 누른다.
3. 서버가 선택한 조건으로 점심 후보를 필터링하고 규칙 기반 점수와 소량의 탐색을 적용한다.
4. 화면에 음식 한 개와 짧고 검증 가능한 추천 이유를 표시한다.
5. 사용자는 `이걸 먹을래요` 또는 `다른 메뉴 뽑기`를 선택한다.
6. 수락 또는 재추천 이벤트가 추천 노출과 연결되어 저장된다.

선택적으로 이메일 회원가입·로그인을 하면 추천 이력이 서버가 확인한 계정에 귀속된다.

## Functional Requirements

- `POST /api/v1/recommendations`는 익명 사용자 ID, 선택적 상황 정보와 다중 필터를 받아 추천 한 개를 반환한다.
- 필터는 같은 그룹 안에서 OR, 서로 다른 그룹 사이에서 AND로 계산하며 빈 그룹은 제한하지 않는다.
- 온도는 뜨거운 것·차가운 것, 종류는 밥·빵·면, 나라는 한식·중식·양식·일식·동남아식·그 외, 맵기는 매운 것·안 매운 것을 제공한다.
- 추천 결과는 음식, 추천 이유, 정책 버전, 추천 ID를 포함한다.
- `POST /api/v1/recommendations/{id}/feedback`은 `ACCEPTED`, `REROLLED`, `REJECTED`, `ATE`, `FAVORITED`, `DISLIKED`를 기록한다.
- 동일 사용자의 최근 선택은 반복 패널티와 속성 선호 계산에 반영한다.
- 추천 세션은 후보 수, 선택 확률, 점수 구성, 정책 버전을 기록한다.
- 관리 명령으로 검수된 초기 음식 데이터를 반복 실행 가능하게 적재한다.
- 초기 카탈로그는 300개 이상의 고유 메뉴와 완전한 추천 속성을 제공한다.
- 대형 카탈로그에서도 후보 풀은 음식군별로 순환 구성해 한 종류가 독점하지 않게 한다.
- 이메일 회원가입, 로그인, 현재 사용자 확인, 로그아웃을 제공한다.
- 비밀번호를 검증·해시하고 로그인 요청을 제한하며, 클라이언트가 계정 ID를 위조할 수 없게 한다.

## Non-functional Requirements

- 로컬 개발은 SQLite로 즉시 실행 가능해야 한다.
- PostgreSQL 연결 정보가 제공되면 같은 모델과 마이그레이션으로 전환되어야 한다.
- API 응답 목표는 로컬 데이터 500개 이하에서 300ms 미만이다.
- 필터 팝업, 레버, 수락, 재추천은 키보드와 스크린리더로 사용할 수 있어야 한다.
- `prefers-reduced-motion`에서는 핵심 애니메이션을 제거한다.
- 비밀 값은 저장소나 Obsidian에 저장하지 않는다.

## Initial Food Representation

음식은 정규화 가능한 대표 이름, 복수 주식 종류와 MVP용 수치 속성 맵을 가진다.

```text
spicy, broth, light, protein, adventurous, cold, familiar, popularity
staple_types: rice, bread, noodle (zero or more)
```

알레르기와 식이 제한은 향후 점수가 아닌 하드 필터로 추가한다.

## Success Criteria

- 새 개발 환경에서 한 번의 설치 절차로 프런트엔드와 백엔드가 실행된다.
- 레버부터 피드백 저장까지 첫 수직 슬라이스가 자동 테스트를 통과한다.
- 추천 요청마다 세션과 노출 레코드가 정확히 하나씩 생성된다.
- 재추천은 약한 부정 신호로 기록되고, 노출되지 않은 음식은 부정 데이터가 되지 않는다.
- 프런트엔드 빌드, 타입 검사, 린트와 백엔드 테스트·린트가 모두 통과한다.
- 시드 명령을 반복 실행해도 메뉴가 중복되지 않고 모든 추천 속성이 0~1 범위를 유지한다.
- 복수 필터를 적용한 추천은 반환된 모든 후보가 그룹별 OR·그룹 간 AND 조건을 만족한다.

## Non-goals

- GraphSAGE, HGT, LightGCN 학습 또는 서빙
- pgvector와 벡터 검색
- 이메일 인증, 비밀번호 재설정, 소셜 로그인
- 식당 위치, 영업시간, 배달 가능 여부 연동
- 유료 운영 인프라와 결제
- 추천 확률을 사용자에게 정밀한 백분율로 표시

## Risks

- `REROLLED`는 음식 비선호 외에도 가격, 접근성, 기분을 섞은 약한 신호다.
- 실제 식당 가용성이 없으면 추천이 실행 가능한 점심 결정으로 이어지지 않을 수 있다.
- 작은 데이터에서 개인화 효과를 과대평가할 수 있다.
- 한 메뉴 반복률을 과도하게 줄이면 사용자의 확실한 선호를 방해할 수 있다.

## Evidence Gates For Later ML

- LightGCN: 다수 사용자의 겹치는 User–Food 상호작용이 생기고 단순 협업 필터링 기준선이 측정된 뒤 검토한다.
- GraphSAGE/HGT: 콘텐츠 기반 모델 대비 이종 관계 사용의 추가 이득을 제거 실험으로 입증한 뒤 검토한다.
- pgvector: SQL 필터와 인메모리 점수 계산이 후보 검색 병목으로 측정된 뒤 도입한다.

## Human Approval Points

- 공개 저장소와 Vercel·Neon 배포는 2026-08-11 사용자가 승인했다. 결제, 위치 센서 수집, 외부 데이터 제공자 연결은 별도 승인 없이는 수행하지 않는다.
